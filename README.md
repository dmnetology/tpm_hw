# Отчёт по Домашнему заданию 6. Volatile и atomic-переменные

Три инструмента без блокировок: остановка потока через volatile-флаг, счётчик на AtomicInteger и singleton-кэш на AtomicReference. В конце — сравнение производительности и корректности AtomicInteger, volatile int и обычного int под конкуренцией потоков.

## Ход работы

1. **Остановка потока через volatile.** FlagWorker крутится в рабочем цикле, на каждой итерации проверяя volatile-флаг stopRequested; основной поток после паузы вызывает requestStop() — рабочий поток сразу видит true и выходит из цикла. volatile даёт видимость записи между потоками без блокировок.
2. **AtomicInteger.** AtomicCounter с методами increment() и get(), инкремент — AtomicInteger.incrementAndGet() (CAS-операция процессора). 8 потоков × 100 000 инкрементов одновременно; проверка итогового значения.
3. **AtomicReference.** SingletonCache хранит значение в AtomicReference<String>; getOrCreate() возвращает уже созданное, а когда текущего значения нет — создаёт через compareAndSet(null, значение). CAS выигрывает ровно один поток — создатель печатает себя, дублей значения не бывает.
4. **Сравнение.** три варианта счётчика — AtomicInteger, volatile int (видимое, но не атомарное поле) и обычный int — под одинаковым нагрузочным прогоном (8 потоков × 100 000 инкрементов), по 3 замера после прогрева JIT.

## Что показали замеры

- volatile гарантирует только видимость: флаг остановки сработал без блокировок, а volatile int++ по-прежнему три шага (read → inc → write) — потеряно 465 007 из 800 000 инкрементов, это пример некорректной ситуации;
- AtomicInteger атомарен благодаря CAS (compare-and-swap): ни блокировок, ни потерь, ценой примерно трёхкратных накладных расходов к обычному int в этом прогоне;
- AtomicReference.compareAndSet() решил задачу «создать ровно один раз»: один победитель CAS, все потоки получили одно значение;
- атомарные переменные не заменяют synchronized: они защищают одну переменную, а если критическая секция затрагивает несколько полей — нужен замок.
