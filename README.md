# Отчёт по Домашнему заданию 12. Многопоточные коллекции

Приложение реализует многопоточную систему обработки событий пользователей веб-приложения на коллекциях из java.util.concurrent: события принимаются в неблокирующую очередь, рассылаются слушателям и агрегируются в статистике, а отдельный этап показывает, почему обычные коллекции для этого не годятся.

## Ход работы

1. **Проблема обычной HashMap.** 10 потоков наращивают общий счётчик: пара get/put неатомарна, часть инкрементов теряется. Затем тот же подсчёт на ConcurrentHashMap атомарным merge — потерь нет.
2. **Система событий.** EventSystemService построена на трёх потокобезопасных коллекциях: ConcurrentLinkedQueue — приём событий (неблокирующие offer/poll, при пустой очереди poll возвращает null, паузы делает сам потребитель); CopyOnWriteArrayList — список слушателей (логгер печатает каждое событие, счётчик ведёт статистику); ConcurrentHashMap — счётчики по типам событий атомарным merge.
3. **Производители.** 3 потока-«браузера» по 10 событий (user-1..5, типы LOGIN/VIEW/CLICK/PURCHASE/LOGOUT) публикуют события с паузами — очередь неблокирующая, offer всегда проходит.
4. **Потребитель.** Отдельный поток забирает события из очереди циклом с опросом (poll → при null пауза 2 мс) и рассылает слушателям; после finishProduction() дообрабатывает остаток и завершается.
5. **Подписка на лету.** В середину прогона (после 15-го обработанного события) добавляется слушатель Аудит — CopyOnWriteArrayList позволяет менять список, когда потребитель по нему итерируется: новые слушатели не ломают обход и сразу же получают события.

## Объяснение коллекций

- ConcurrentLinkedQueue — неблокирующая неограниченная очередь на CAS: публикация не тормозится никогда, потребитель сам следит за паузами, poll() при пустоте возвращает null;
- CopyOnWriteArrayList — каждая модификация создаёт копию массива, поэтому итерация слушателей безопасна при подписке/отписке в любой момент; чтение без блокировок — ровно профиль «список слушателей»: много чтений, редкие изменения;
- ConcurrentHashMap — данные делятся по сегментам, вся карта не блокируется; составные операции надо делать встроенными атомарными методами (merge вместо пары get/put);
- HashMap — для сравнения: пара get/put неатомарна, потери обновлений достигают трети.

## Что показали этапы

- обычная HashMap потеряла 3588 из 10 000 обновлений — типичная состояние гонки при неатомарных get/put; ConcurrentHashMap с merge посчитала ровно 10 000;
- 30 событий от 3 производителей обработал один потребитель: очередь приняла все публикации без блокировок;
- слушатель Аудит, добавленный посреди прогона, сразу начал получать события (две покупки) и не вызвал ConcurrentModificationException — CopyOnWriteArrayList отработал как задумано;
- итоговая статистика по типам сходится с числом обработанных событий (6+9+5+5+5 = 30) — атомарные операции merge не теряют инкременты.
