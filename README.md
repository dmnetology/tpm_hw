# Отчёт по Домашнему заданию 8. Пул потоков (Thread Pool)

Приложение проверяет 20 публичных API и выводит сводку: статус-коды, время ответа, состояние пула. Проверка выполняется двумя способами — последовательно и через собственный ThreadPoolExecutor, настроенный вручную, — затем сравнивается время.

## Ход работы

1. **Список URL и задачи.** Список из 20 публичных API (jsonplaceholder, api.github.com, binance, frankfurter, open-meteo, catfact и др.) — без ключей и лимитов, с малыми ответами. UrlProbeTask — Callable, который отправляет GET-запрос RestTemplate'ом с тайм-аутами 5 с, замеряет время ответа и возвращает ProbeResult (статус-код, время, поток); ошибка сети попадает в результат и сводку, а не рушит прогон.
2. **Последовательная проверка.** Тот же список обходится по одному запросу — база для сравнения времени.
3. **Собственный ThreadPoolExecutor.** Настройка вручную: corePoolSize = 4, maximumPoolSize = 8, keepAliveTime = 30 с, ограниченная очередь ArrayBlockingQueue(10), ThreadFactory с именами UrlProbe-N, при переполнении — CallerRunsPolicy. Задачи отправляются submit() — возвращает Future для получения результата. После отправки снимок пула под нагрузкой.
4. **Сбор результатов и завершение.** Результаты достаются через future.get(); затем pool.shutdown() и awaitTermination() — без shutdown() non-daemon потоков пула приложение не завершилось бы; печать сводки и сравнения.

## Результат (вывод программы)

```text
=== Последовательная проверка всех 20 URL ===
Проверено 20 URL за 10575 мс (успешных ответов: 20, ошибок: 0)

=== Собственный ThreadPoolExecutor: 20 URL одновременно ===
Пул под нагрузкой: в пуле 8 потоков, активных 8, в очереди 7
UrlProbe-1: https://jsonplaceholder.typicode.com/posts/1 — код 200, 518 мс
...
main: https://randomuser.me/api/?inc=gender — код 200, 294 мс
Сводка: успешных ответов 20 из 20, ошибок: 0
Пул после работы: потоков создано 8, задач завершено 19, shutdown() отработал: true
Время: последовательно 10575 мс, с пулом 3051 мс — ускорение примерно в 3,5 раза
```

## Объяснение методов

- corePoolSize = 4 — базовые потоки создаются сразу; когда очередь заполнена, пул расширяется до maximumPoolSize = 8; keepAliveTime = 30 с завершает простаивающие сверх базовых потоки;
- ограниченная очередь ArrayBlockingQueue — защита от переполнения памяти под нагрузкой; когда она полна вместе с максимумом потоков, срабатывает RejectedExecutionHandler;
- CallerRunsPolicy перенаправляет задачу в поток вызывающего — в выводе видно, что одна задача выполнена потоком main, то есть подача замедлилась, вместо потери задачи;
- submit() возвращает Future: задачи и результаты разделены, итоги собираются после завершения;
- shutdown() + awaitTermination() — явное завершение пула.

## Что показали замеры

- ускорение примерно в 3,5 раза: 10 575 мс последовательно против 3 051 мс с пулом (4–8 потоков на 20 независимых запросов);
- под нагрузкой пул расширился с 4 до 8 потоков и разложил 7 задач в очередь — алгоритм принятия решений ThreadPoolExecutor виден прямо в выводе;
- CallerRunsPolicy сработала один раз (задача ушла в main) — политика отказа замедлила подачу, не потеряв задачу;
- некоторые API периодически отвечают ошибками (тайм-ауты, 429): сводка учитывает их; список составлен из стабильных хостов, поэтому в этом прогоне ошибок нет.
