# Отчёт по Домашнему заданию 9. Callable и Future

Приложение показывает работу с Callable и Future: отмену долгой задачи через Future.cancel(), запуск Callable напрямую в Thread через FutureTask, пакетный запуск через invokeAll(), периодическую задачу на ScheduledExecutorService и периодический сервис-агрегатор на аннотации @Scheduled.

## Ход работы

1. **Долгая задача и отмена.** LongRunningTask — Callable&lt;String&gt;, имитирует обработку из 10 шагов по 1 секунде (10 секунд работы) и печатает прогресс. Задача отправляется в пул submit() → возвращает Future. Через 3 секунды main вызывает future.cancel(true): метод вернул true, поток задачи прерван на шаге 2–3 из 10 (Thread.sleep отвечает на прерывание). После отмены isCancelled = true, а future.get() бросает CancellationException — результат отменённой задачи получить нельзя.
2. **FutureTask — мост Callable → Runnable.** Callable нельзя передать в new Thread напрямую. FutureTask реализует Runnable и Future одновременно: new Thread(futureTask).start() запускает Callable в отдельном потоке, результат достаётся через futureTask.get(). Тот же приём ExecutorService использует под капотом в submit() — оборачивает Callable в FutureTask.
3. **invokeAll() — пакетный запуск.** Пять задач RandomResultTask (Callable&lt;Integer&gt;), каждая имитирует работу случайное время от 1 до 3 секунд и возвращает число. Пул на 5 потоков — все задачи стартуют одновременно; invokeAll() блокирует вызывающий поток до завершения всего пакета и возвращает список Future в порядке отправки, все с isDone = true; время пакета равно времени самого долгого члена группы.
4. **ScheduledExecutorService.** Периодическая задача «проверка статуса системы» запускается scheduleAtFixedRate() раз в секунду: печатает занятую память heap и число потоков JVM. Через 5 запусков расписание отменяется через ScheduledFuture.cancel(false) — отмена касается только расписания, текущий запуск не прерывается.
5. **Часть 2: PeriodicDataAggregator.** Периодический сервис с @Scheduled(fixedRate = 2 с) — для работы аннотации приложение включено @EnableScheduling. Каждый тик: список из 5 валют, для каждой отправляется Callable в собственный пул потоков (именами fetch-N). Внешний источник имитируется методом fetchRate(): случайная задержка 150–700 мс, с вероятностью 20% — IOException («источник недоступен»). Исключение перехватывается пулом и при Future.get() приезжает обёрнутым в ExecutionException, в тике обрабатывается через getCause(). Успешные курсы логируются и сохраняются в таблицу последних значений.
6. **Окно демонстрации.** Приложение живёт постоянно, а тики включаются на время демонстрации: runner включает флаг и ждёт CountDownLatch, агрегатор после 5 тиков печатает сводку и освобождает runner.

## Объяснение методов

- submit(Callable) — запускает задачу в пуле и возвращает Future; сам пул под капотом оборачивает Callable в FutureTask;
- cancel(true) — прерывает поток выполняющейся задачи; это работает, потому что LongRunningTask ждёт в Thread.sleep и выбрасывается InterruptedException; для периодической задачи cancel(false) снимает только расписание;
- get() — блокирует вызывающий поток (нужен timeout-вариант через get(timeout) для страховки от зависания); после отмены бросает CancellationException, при ошибке в задаче — ExecutionException с исходным исключением в getCause();
- invokeAll() — пакетный запуск всех задач сразу с ожиданием их всех: удобно, когда нужны результаты всего набора;
- scheduleAtFixedRate() — расписание с фиксированной частотой (интервал считается от старта запуска); @Scheduled(fixedRate) — то же самое средствами Spring.

## Что показали этапы

- cancel(true) вернул true, задача реально прервана на шаге 2–3 из 10: отмена действует, если задача отвечает на прерывание;
- get() после отмены бросает CancellationException: у отменённой задачи нет результата;
- пять задач с разной работой (1.3–3 с) заняли в пакете 2972 мс — invokeAll стоил времени самого долгого члена группы, а не суммы;
- ошибки задач не пропадают: IOException из имитируемого источника приезжает из Future.get() обёрнутым в ExecutionException, доступ к первопричине — через getCause();
- за 5 тиков агрегатора выполнено 25 запросов: 21 успешный, 4 сбоя; сбой одной валюты не мешает остальным — следующий тик снова опрашивает все 5.
