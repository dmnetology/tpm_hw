# Отчёт по Домашнему заданию 10. CompletableFuture (асинхронное программирование)

Приложение по списку из 5 идентификаторов товаров собирает данные из двух независимых источников (товары и курс валют) — синхронно и через CompletableFuture — обогащает каждый результат, объединяет цену и курс в итоговый объект и сравнивает время обеих версий.

## Ход работы

1. **Доменная модель.** ProductData — товар из источника: id, название, цена в USD (категория появляется после обогащения); FinalResult — итоговый объект: товар + категория + курс + цена в рублях. Товаров пять (sku-1..sku-5); sku-3 — имитация сбоя одного из источников данных.
2. **Синхронная версия.** По каждому id последовательно: запрос товара (300–800 мс) → обогащение (100–300 мс) → запрос курса (200–500 мс) → комбинация. Сбой ловится на месте — объект пропускается, остальные добираются.
3. **Основной метод fetchAllDataAsync(List&lt;String&gt; ids).** Для каждого id строится цепочка: supplyAsync(fetchProduct, executor) → thenApplyAsync(enrich, executor) — «тяжёлое» обогащение (категория по справочнику) уходит в собственный пул, а не в поток источника; параллельно supplyAsync(fetchRate, executor) запрашивает второй независимый источник — курс; thenCombine(product, rate) объединяет оба результата в FinalResult (цена в рублях = цена USD × курс); thenAccept печатает факт готовности каждой цепочки по мере готовности; handle отлавливает сбой цепочки и возвращает null — такой объект пропускается при сборке списка (join + filter).
4. **Собственный Executor.** FixedThreadPool(8) с именованными демон-потоками cf-worker-N — все supplyAsync и thenApplyAsync идут в нём, commonPool не используется.
5. **Трассировка.** Каждая строка лога содержит имя потока и ID запроса (сквозной счётчик req-N) — видно, кто что выполнял.
6. **Завершение пула.** После демонстрации shutdown() + awaitTermination(); при остановке Spring-приложения — @PreDestroy с shutdownNow() на случай, если демонстрация не выполнялась.

## Объяснение методов

- supplyAsync(..., executor) — запуск запроса к источнику в собственном пуле, а не в ForkJoinPool.commonPool;
- thenApplyAsync(enrich, executor) — тяжёлое (блокирующее) преобразование уходит в пул, не блокируя поток источника и main;
- thenCombine(productFuture, rateFuture) — объединение двух независимых результатов в один объект, срабатывает после завершения обоих;
- thenAccept — потребление готового результата без возврата нового значения;
- handle((result, ex) → ...) — обработка и успеха, и ошибки: при сбое в цепочке печатает причину (getCause из CompletionException) и возвращает null, поэтому операция в целом возвращает частичный результат.

## Что показали этапы

- в синхронной версии всё выполняет поток main; в асинхронной — только cf-worker-N: пул реально работает, commonPool не задействован;
- обогащение sku-4 выполнено потоком cf-worker-2, а его получение — cf-worker-7: thenApplyAsync переносит работу между потоками пула;
- сбой sku-3 изолирован через handle: обе версии вернули 4 из 5 объектов, остальные товары не пострадали;
- логи с req-N позволяют проследить каждую сущность через весь конвейер: запрос → обогащение → готовность;
- ускорение примерно в 4 раза: 4640 мс последовательно против 1157 мс асинхронно — пять независимых цепочек идут одновременно, время равно самому медленному конвейеру, а не сумме.
