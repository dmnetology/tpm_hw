# Отчёт по Домашнему заданию 7. Deadlock, Livelock, Starvation

Программа воспроизводит три классические проблемы многопоточности, диагностирует их и показывает приёмы предотвращения. Deadlock подтверждается тремя способами: состояниями потоков, ThreadMXBean и дампом потоков jstack.

## Ход работы

1. **Deadlock.** DeadlockWorker захватывает два ресурса в заданном порядке; запущены два потока: Deadlock-1 берёт resourceA, затем resourceB, Deadlock-2 — resourceB, затем resourceA. Пауза 200 мс между захватами гарантирует, что каждый закрепил свой первый ресурс, когда пытается взять второй. Через 2 с оба потока в BLOCKED, ThreadMXBean.findDeadlockedThreads() подтверждает взаимную блокировку; в этот момент снимается дамп потоков.
2. **Дамп потоков.** jstack <pid>: в дампе секция «Found one Java-level deadlock» называет оба потока, мониторы и владельцев, а в стеке видно, чей замок уже захвачен и какой ждёт — цикл «Deadlock-1 держит ресурс, которого ждёт Deadlock-2, и наоборот».
3. **Livelock.** LivelockWorker: владея общим ресурсом, поток уступает его «голодному» соседу; сосед уступает обратно. Состояние ресурса постоянно меняется (потоки активны), но задач никто не выполняет.
4. **Выход из livelock.** Число уступок ограничено лимитом (3 подряд, счётчик сбрасывается после выполнения задачи) — после нескольких передач поток выполняет задачу сам, прогресс возвращается.
5. **Starvation.** Несправедливая ReentrantLock, жадный поток в плотном цикле держит замок большую долю времени; голодный поток пытается получить ресурс методом tryLock() с тайм-аутом и считает неудачи.
6. **Предотвращение starvation.** Та же пара потоков на справедливой ReentrantLock(true): замок раздаётся по очереди, голодание исчезает.

## Дамп потоков (jstack)

```text
Found one Java-level deadlock:
=============================
"Deadlock-1":
  waiting to lock monitor 0x0000025fc9ca0d00 (object 0x00000006117232e0, a com.example.demo.Resource),
  which is held by "Deadlock-2"

"Deadlock-2":
  waiting to lock monitor 0x0000025fcaf793f0 (object 0x0000000611723298, a com.example.demo.Resource),
  which is held by "Deadlock-1"

...стеки:

"Deadlock-1":
	at com.example.demo.DeadlockWorker.run(DeadlockWorker.java:32)
	- waiting to lock <0x00000006117232e0> (a com.example.demo.Resource)
	- locked <0x0000000611723298> (a com.example.demo.Resource)
"Deadlock-2":
	at com.example.demo.DeadlockWorker.run(DeadlockWorker.java:32)
	- waiting to lock <0x0000000611723298> (a com.example.demo.Resource)
	- locked <0x00000006117232e0> (a com.example.demo.Resource)

Found 1 deadlock.
```

Дамп объясняет deadlock в точности: оба потока стоят в BLOCKED на мониторе объекта Resource, jstack проверил граф ожиданий и нашёл цикл — Deadlock-1 уже держит ресурс, принадлежащий Deadlock-2, и наоборот. Ни один из них не может продолжиться, пока другой не освободит замок, а освобождать нечем, кроме как выйдя из заблокированного кода.

## Что показали этапы

- противоположный порядок захвата — пример некорректной ситуации: deadlock, потокам навсегда перекрыт путь дальше;
- единый порядок захвата у всех потоков — корректная ситуация: цикл ожиданий невозможен, оба потока завершаются;
- бесконечная уступчивость — livelock: потоки не заблокированы и активно работают, CPU занят, но задач — ноль;
- лимит уступок (аналог выхода по тайм-ауту из бесконечного цикла) — livelock прекращается, задачи выполняются;
- несправедливая блокировка и плотный конкурент — starvation: за 2 с голодный поток получил ресурс 1 раз против 465 у жадного, 93 попытки истекли по тайм-ауту;
- справедливая блокировка — starvation исчезает: ресурс достаётся обоим по очереди (2345 против 476 — очередь честно чередует потоки).
