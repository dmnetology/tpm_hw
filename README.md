# Отчёт по Домашнему заданию 11. Fork/Join Framework

Приложение считает количество агрегированных элементов каталога из прошлых заданий — товаров с ценой в рублях выше порога — на массиве из 50 млн цен. Подсчёт выполняется тремя способами: последовательно, рекурсивной задачей Fork/Join и разбиением на пачки, где каждая пачка — новая задача.

## Ход работы

1. **Данные.** Генерируется массив из 50 000 000 цен в рублях (данные агрегации каталога, как priceRub в задании 10, случайные значения 10 000–200 000). Агрегат: количество товаров дороже 90 000 руб.
2. **Последовательный подсчёт.** Один цикл по массиву — база для сравнения.
3. **Рекурсивная задача.** CountingTask — RecursiveTask&lt;Long&gt;: если диапазон больше порога разбиения (4 млн), он делится пополам; левая половина уходит fork() в очередь (её может украдет другой воркер), правая считается в текущем потоке, суммы складываются после join(). На каталоге получается дерево из 31 пачки-задачи (16 листовых).
4. **Батчи.** Каталог размечается на 13 непересекающихся пачек (по не более 4 млн цен); каждая пачка — отдельная листовая задача BatchCountTask, все отправляются в пул submit(), результаты собираются join().
5. **Собственный ForkJoinPool.** new ForkJoinPool(16, фабрика именованных воркеров fj-worker-N, обработчик ошибок, asyncMode = false — LIFO-очередь лучше подходит рекурсии). commonPool не используется; parallelism берётся по числу ядер.
6. **Диагностика work-stealing.** После каждого параллельного прогона печатается getStealCount() и поток каждой листовой пачки.

## Объяснение методов

- fork() — кладёт подзадачу в очередь текущего воркера, при простое другой воркер крадёт её (work-stealing); join() — блокирует до готовности и возвращает результат; compute() — тело задачи с условием разбиения;
- pool.invoke(root) — синхронный запуск корневой задачи: воркеры раскручивают всё дерево рекурсивно;
- pool.submit(task) + task.join() — разметка на пачки: независимые листовые задачи без дерева разбиения;
- getStealCount() — сколько задач воркеры взяли из чужих очередей; вместе с именами воркеров в печати пачек показывает work-stealing в действии.

## Что показали этапы

- все три версии нашли одно и то же: 28 947 925 из 50 000 000 — разбиение корректно;
- работа воркеров видна по именам: 16 пачек рекурсивного прогона распределились по fj-worker-1..16, краж — 16 и 13 в параллельных прогонах;
- на простом подсчёте (одно сравнение на элемент) Fork/Join не даёт выигрыша: 28 мс последовательно против 63 мс рекурсивно и 51 мс батчами — накладные расходы на разбиение, очереди и кражи сопоставимы с самой работой, а подсчёт упирается в скорость памяти; Fork/Join эффективен на CPU-интенсивных задачах — слишком мелкая работа на элемент съедает выигрыш (прямо из списка случаев, когда Fork/Join стоит избегать);
- батчи проще: 13 самостоятельных задач вместо дерева из 31 пачки; деление пополам в рекурсивной версии автоматически балансирует нагрузку между воркерами.
