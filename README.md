# Отчёт по Домашнему заданию 13. BlockingQueue и Producer-Consumer

Приложение реализует «сервер задач» по примеру из задания: два производителя кладут URL-задачи в ограниченную BlockingQueue, два потребителя забирают их, скачивают страницы и извлекают заголовок. Переполнение и опустошение очереди обрабатываются средствами BlockingQueue.

## Ход работы

1. **Модель.** UrlTask — record с URL; UrlProducer — Runnable, кладущий задачи; UrlConsumer — Runnable, обрабатывающий их. Очередь — ArrayBlockingQueue(3): ограниченная, оба режима (переполнение/опустошение) проявляются сразу.
2. **Производители.** По 5 URL российских ресурсов (netology.ru, interfax.ru, mos.ru, vk.com, cbr.ru; ria.ru, lenta.ru, rg.ru, cnews.ru, ok.ru). put() кладёт задачу и блокируется, если очередь полна; перед ним печатается состояние по remainingCapacity(). Темп имитирует реальную нагрузку: первые три задачи идут почти без паузы (пачка — очередь переполняется), затем пауза ~2,5 с между оставшимися (потребители разгребают — очередь опустошается).
3. **Потребители.** poll(1000 мс) вместо take(): очередь пуста — потребитель печатает «жду задачи» и продолжает, а не ждёт вечно. Забрав задачу — скачивает страницу RestTemplate'ом с тайм-аутами (как в задании 8) и извлекает заголовок &lt;title&gt; регуляркой; печатает сайт, заголовок и время. Потребители работают, пока не поданы все задачи и очередь не пуста.
4. **Сводка.** После завершения — общее количество и распределение задач между потребителями.

## Объяснение методов

- put() — блокирующая публикация: если очередь полна, производитель ждёт, пока потребитель освободит место; задача не теряется и не отклоняется — переполнение обрабатывается самой очередью;
- poll(timeout) — блокирующее потребление с тайм-аутом: при опустошении потребитель ждёт максимум секунду и печатает состояние; бесконечный take() оставил бы потребителя ждать навечно;
- remainingCapacity() — печать переполнения перед put(): сколько мест осталось;
- BlockingQueue координирует производителей и потребителей сама — без ручных wait/notify из задания 4;
- RestTemplate + регулярка — реализация «скачивает страницу и извлекает заголовок» из примера задания.

## Что показали этапы

- пачка задач переполнила очередь трижды: напечатались «очередь полна — put() ждёт места» — производители реально блокировались, переполнение обработано без потери задач;
- между пачками очередь опустошалась: потребитель напечатал «очередь пуста — жду задачи» по тайм-ауту поллинга, дождался новой задачи от производителя и продолжил работу — опустошение не рвёт конвейер и не ждёт вечно;
- балансировка сама: 10 задач легли на потребителей неравномерно (3 и 7) — consumer-1 был занят долгими загрузками, свободный потребитель забирал следующую задачу;
- все 10 страниц скачаны с российских ресурсов, заголовки извлечены: конвейер производитель → очередь → потребитель работает от первой до последней задачи.
